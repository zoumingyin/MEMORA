# MEMORA V0.9 升级指南

- 适用版本：MEMORA `0.9.0`
- 适用平台：Windows 10/11 x64
- 应用标识：`com.bianqian.desktop`
- 升级方式：NSIS 覆盖安装
- 发布日期：2026-11-18

> **验证状态：** 本轮没有对正式 0.9.0 安装包执行覆盖升级。此前阶段做过独立 identifier 的 `0.2.0 → 0.2.1` 覆盖升级、静默卸载和重装验证，其结果只作为流程参考，不能替代正式包的 0.9.0 升级验收。正式升级需在隔离环境或用户确认停机后补做。

---

## 1. 升级前须知

### 1.1 版本关系

- 本轮已将 `package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock` 统一为 `0.9.0`。
- 安装包文件名、文件版本和产品版本均为 `0.9.0`。
- 此前本地正式制品为 `0.2.0`。从 `0.2.0` 覆盖安装到 `0.9.0` 属于版本号上升，NSIS 会按升级流程处理。
- 本轮未修改 SQLite 表结构或迁移，迁移仍为 1–9，因此 `0.2.0` 数据库可直接被 `0.9.0` 读取。

### 1.2 升级不会自动执行的操作

- 不会自动上传或同步用户数据。
- 不会自动切换当前 AI 模型。
- 不会自动删除执行历史。
- 不会自动重建业务数据库。
- 不会删除旧 migration。

### 1.3 已知不兼容

本轮未发现业务数据不兼容。迁移 1–9 为向前兼容，没有 down migration。

如需回退到旧版本，应使用升级前备份恢复数据库，而不是直接安装旧程序后继续使用新 schema。

## 2. 升级前备份

推荐同时做两层备份。

### 2.1 应用内备份

1. 启动 MEMORA。
2. 进入“设置 > 数据”。
3. 点击“备份数据库”。
4. 选择应用数据目录以外的位置。
5. 记录备份文件路径和大小。

### 2.2 文件级备份

彻底退出应用后，复制：

```text
%APPDATA%\com.bianqian.desktop\bianqian.db
%APPDATA%\com.bianqian.desktop\ai-config.json
```

如存在 WAL / SHM 文件，一并复制：

```text
%APPDATA%\com.bianqian.desktop\bianqian.db-wal
%APPDATA%\com.bianqian.desktop\bianqian.db-shm
```

备份目录不要放在安装目录中，避免卸载时被清理。

### 2.3 自动备份

可在设置中开启“每日自动备份”。应用启动时会复制数据库，保留最近 7 份。升级前建议确认“最近备份时间”不是很久以前。

---

## 3. 升级步骤

1. 记录当前版本和当前数据量（便签数量、执行历史条数等）。
2. 完成备份。
3. 通过托盘菜单彻底退出 MEMORA，确认进程不在运行。
4. 运行 `MEMORA_0.9.0_x64-setup.exe`。
5. 在安装程序中选择与当前安装相同的目录，执行覆盖安装。
6. 等待安装完成，从开始菜单或桌面快捷方式启动。
7. 检查数据、AI 配置和执行历史。
8. 检查设置中的主题、透明度和窗口选项是否保持。

静默升级可执行：

```powershell
.\MEMORA_0.9.0_x64-setup.exe /S /UPDATE
```

除非在受控维护环境中，否则建议使用交互式安装，便于确认安装目录和错误提示。

> 安装包使用产品名 `MEMORA` 注册卸载信息。若机器上同时存在旧产品名安装目录，请先确认旧程序的卸载入口和安装目录，避免出现两个入口指向不同副本。

## 4. 升级后验证清单

| 检查项 | 预期 |

## 5. 升级验证现状

### 5.1 本轮未执行

- 正式 `com.bianqian.desktop` 0.9.0 安装包的覆盖安装；
- 升级前后的数据保留比对；
- 正式包的卸载与重装。

原因：本机正式应用正在运行并使用真实数据库；正式安装包与现有安装共用 `MEMORA` 卸载注册键和应用数据目录，直接安装/卸载会改动用户现有环境。本机没有 Windows Sandbox，无法提供同 identifier 的隔离桌面。

### 5.2 可参考的历史隔离结果

此前阶段使用独立产品名 `MEMORA ReleaseCheck`、独立 identifier `com.bianqian.releasecheck`、独立数据目录和独立 Cargo target，验证过：

| 检查项 | 结果 |
| --- | --- |
| 0.2.0 静默安装 | exit 0 |
| 安装后启动 | 成功 |
| 便签 / AI 配置 / 执行历史 | 可读 |
| 数据库备份 | 成功 |
| 0.2.1 覆盖升级 | exit 0 |
| 升级后数据 | 保留 |
| 静默卸载 | exit 0，数据和快捷方式按预期处理 |
| 重装 | 成功，数据可读 |

这些结果不包含 0.9.0 版本和正式 identifier，因此**不能**作为本轮正式安装验收结论。

3. 对比升级前后的便签、待办、提醒、废纸篓、AI 配置和执行历史；

## 6. 数据库迁移说明

- 应用启动时由 SQL 插件自动执行迁移。
- 迁移记录保存在 `_sqlx_migrations`。
- 迁移 9 执行：

```sql
ALTER TABLE agent_execution_steps ADD COLUMN proposal_id TEXT;
```

- 旧步骤的 `proposal_id` 保持 `NULL`，不会被伪造。
- 重复启动不会重复执行迁移。
- 旧库 v8 升级到 v9 后，旧便签和旧执行历史均保留。

### 6.1 迁移失败

此前阶段做过迁移冲突注入：数据库版本记录停留在 8，但 `proposal_id` 列已存在，使迁移 9 再次执行时冲突。

结果：

- 应用启动失败，退出码 101；
- 业务数据保留；
- `_sqlx_migrations` 仍只有 1–8，没有写入半条迁移记录；
- 再次启动仍然失败；
- 没有自动删除数据库，也没有自动修复。

本轮未修改迁移代码。升级前备份仍是必要步骤。

## 7. 回退与恢复

### 7.1 回退应用

1. 卸载当前版本（保留应用数据）。
2. 安装旧版本。
3. 如旧版本不能识别新 schema，使用升级前备份覆盖数据库。
4. 启动并确认数据。

### 7.2 恢复数据库

应用内：

1. 打开“设置 > 数据”。
2. 点击“恢复数据库”。
3. 选择备份文件。
4. 彻底退出并重启应用。

应用无法启动时：

1. 彻底结束 MEMORA 进程。
2. 备份当前 `bianqian.db`、`bianqian.db-wal`、`bianqian.db-shm`。
3. 将备份文件复制为 `%APPDATA%\com.bianqian.desktop\bianqian.db`。
4. 删除残留的 `bianqian.db-wal` 和 `bianqian.db-shm`。
5. 重新启动应用。

不要在没有复制当前文件的情况下直接覆盖。

---

## 8. 卸载与重装

- 交互式卸载默认保留应用数据，除非用户勾选“删除应用数据”。
- 静默卸载保留应用数据。
- 重装后会读取原 `%APPDATA%\com.bianqian.desktop` 数据。
- 安装目录只包含程序文件，不包含用户数据库。

正式 0.9.0 包的卸载与重装尚未在本轮执行，需按第 5.3 节补测。

## 9. 升级失败排查

| 现象 | 处理 |
| --- | --- |
| 安装程序无法覆盖 | 确认应用已退出，包括托盘进程 |
| 启动后数据为空 | 确认启动的是同一安装和新数据目录；不要立即新建大量数据 |
| AI 配置丢失 | 检查 `ai-config.json` 是否仍在应用数据目录；用备份恢复 |
| 执行历史缺失 | 检查数据库是否为升级前副本；不要清空数据库 |
| 启动立即退出 | 可能是迁移冲突；保留数据库，使用备份恢复 |
| 恢复后无变化 | 恢复在下次启动生效，需彻底退出再启动 |
| 出现未知发布者 | 安装包未签名，核对 SHA-256 后决定是否继续 |

## 10. 发布前升级条件

正式发布前，发布负责人应：

1. 完成发布提交，并从该提交重建安装包；
2. 使用正式制品在隔离机器做一次完整安装、覆盖升级、卸载和重装验证；
3. 记录最终安装包大小和 SHA-256；
4. 确认代码签名策略；
5. 不把历史隔离验证的制品哈希与正式制品混用。
