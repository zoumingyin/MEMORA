## 结论摘要

1. **任务理解**：系统提示词新增 6 条硬规则（任务分类、不把猜测当指令、依赖顺序、先问再做、失败如实、上限与小结）；执行层不再依赖模型「自觉」，所有写入都经过 Phase 2 的参数校验与回读确认。
2. **多步任务**：同一轮的全部 `tool_calls` 严格串行、按模型给出的顺序执行；后一步只能使用前一步真实返回的 id；删除仍然只生成确认卡片。
3. **多工具编排**：保留原有 agent loop 机制，只把编排逻辑抽成纯函数；轮次上限从「静默结束」改为确定性的「已完成 / 未执行 / 失败」清单。
4. **歧义处理**：同名便签在搜索结果中附加确定性提醒；一个提醒有多个待触发闹钟且未指定 `alarm_id` 时，执行器直接拒绝并标记「等待补充」，不修改任何闹钟、不丢失重复规则。
5. **执行反馈**：8 个真实阶段（理解 / 搜索 / 执行 / 整理 / 已完成 / 部分完成 / 执行失败 / 等待补充），只在真实阶段切换时更新；终态徽标与执行记录都来自工具真实返回。
6. **结果小结**：每条执行记录带结构化 `effect`（操作类型、条目标题、真实 id、数量），小结不虚构 id、标题、时间或状态；明细可展开查看每一步。
7. 自动化测试 **101/101 通过**（18 suites，本阶段新增 24 条）；类型检查、Lint、Vite 构建、Windows 安装包构建全部成功。

## 二、任务理解机制

### 2.1 提示词层（模型侧）

`src/services/agentToolSchema.ts:168`–`173` 新增 6 条规则：

| 规则 | 内容 |
| --- | --- |
| 11 | 先判断任务类型：提问/闲聊只查询回答；只有明确要求才新建/修改；删除只生成确认卡片；不把猜测、举例、「也许可以」当成指令，绝不擅自增删改 |
| 12 | 多步任务先在内部列步骤，按依赖顺序执行：先检索确认对象 → 读取必要内容 → 写入或汇总；必须使用前一步返回的真实 id，不跳过必要查询，不重复执行已成功的步骤 |
| 13 | 信息不足先问再做：目标不唯一（同名/相似便签、一个提醒多个闹钟、多个候选提醒）、要改的内容或时间不明确时，列出候选并询问；不自行挑第一条、不批量修改、不猜测 |
| 14 | 步骤失败后如实说明，不假设后续已完成，不把未执行说成完成；总结必须区分已完成与未完成 |
| 15 | 收到「已达到工具调用上限」提示时，必须说明已完成与未执行，并请用户回复「继续」，不得声称全部完成 |
| 16 | 结束前给结果小结：用户要求了什么、实际完成了什么（含标题）、失败/未执行项、等待确认的删除；只写工具真实返回的事实，不虚构 id、标题、时间或状态 |

`src/services/assistantContext.ts:179` 的上下文规则同步收紧：不执行用户未明确要求的写操作；目标不唯一、时间或内容不明时先询问；多步任务说明实际完成与未完成。

### 2.2 执行层（确定性兜底）

- 模型即使误判，也无法绕过 Phase 2 的校验：`create_entry` / `update_entry` 逐字段校验、写后回读确认（`src/services/agentToolExecutor.ts`）。
- `delete_entry` 无论如何只返回确认卡片，不写库（`src/services/deleteExecution.ts` 保持不变）。
- 未指定目标 id 的修改/删除直接失败，不存在「按标题猜一条」的路径。
- 每次工具执行前检查请求作用域，停止后不再执行任何未开始的工具。

## 三、多步任务流程

以「整理我的项目开发记录，并创建三个后续待办」为例，真实执行链为：

1. 模型先输出 `search_notes`（可能多轮关键词）。
2. 执行器回传真实 id 与内容摘要（超长截断，完整内容由 `get_note` 读取）。
3. 模型按需 `get_note` 读取具体条目。
4. 模型提取信息后，同一轮或下一轮连续发出 3 个 `create_entry`。
5. 执行器按顺序真实写库，每步写后回读，返回真实 `entryId` 与标题。
6. 模型输出汇总；面板显示「执行记录 · N 步」及「新建 3 项：待办「…」、…」。

关键保证：

| 要求 | 实现 |
| --- | --- |
| 同批次按顺序执行 | `executeToolBatch` 严格按数组顺序串行，不并发（`src/services/agentExecution.ts:146`） |
| 跨轮次结果传递 | 工具结果在该批次结束后写回 `role:'tool'` 消息，`tool_call_id` 与调用一一对应（`src/services/agentExecution.ts:171`） |
| 不跳过必要查询 | 提示词规则 12 + 模型必须持有 id 才能修改/删除 |
| 不重复成功操作 | Phase 2 的 `tool_call_id` 去重 + 请求内写签名去重，重复调用标记「已跳过」 |
| 失败后不假装完成 | 失败结果照实回传；终态推导只在全部成功时为「已完成」 |

### 3.1 同批次与跨轮次的边界（Phase 3.1 修正）

- **同一批次**：模型在一轮响应里同时给出的多个 `tool_calls` 彼此独立。工具按模型给出的顺序串行执行，但模型在发出这些调用时看不到其中任何一个的结果；本批次的结果只在全部执行完后一次性回传。串行只保证执行顺序，不构成「后一个调用能动态读取前一个结果」。
- **跨轮次**：需要前一步结果的操作必须等下一轮。例如 `search_notes` → 结果回传模型 → 模型用真实 `entryId` 发出 `update_entry`。
- 因此「查询后修改」不是同批次能力；同批次里用猜测 id 发出的修改会因找不到目标而失败，不会自动替换成查询结果里的 id。

## 四、多工具编排

### 4.1 循环结构（保留原机制）

`src/store/useAssistantStore.ts:439`–`652` 的 agent loop 结构未变：请求 → 判定 `toolCalls` / `done` / `error` → 执行工具 → 结果回传 → 续问。

本阶段只做三件事：

1. 把批次执行、汇总、上限提示、终态推导抽到 `agentExecution.ts`，便于测试。
2. 每轮请求前设置真实阶段：首轮 `understanding`，工具轮之后 `composing`；工具批次只读时 `searching`，含写入时 `executing`。
3. 达到 `MAX_TOOL_ROUNDS = 8` 时，不再执行本轮调用，改为追加确定性提示并结束（`src/services/agentExecution.ts:287`）。

### 4.2 轮次上限反馈

提示内容只陈述可确定的事实：

```
已达到本次回答的工具调用上限（8 轮），以下为实际执行情况：
已完成 2 项（新建 1 项：待办「补测试」；搜索资料 1 次：搜索便签）
尚未执行的调用 1 项：新建待办「写文档」。如需继续，请回复「继续」，我会接着处理剩余步骤。
```

- 「已完成」只统计 `status = ok / confirm` 的步骤，失败项单列，不会被算进已完成。
- 「尚未执行」来自本轮模型请求但被上限拦下的调用，不推测模型中还「想」做什么。
- 终态为 `partial`，`toolLimitReached = true`，面板显示「部分完成」。
- 用户停止时同样不会静默：已完成写入保留记录，未开始的工具不执行，终态按实际成功数推导。

### 4.3 部分失败

- 单个工具失败不中断后续工具（失败的 `role:'tool'` 结果照常回传，模型可据此调整）。
- 成功写入不回滚，执行记录保留成功项。
- 终态：有成功也有失败 → `partial`；全部失败 → `failed`；请求级错误（网络/鉴权）→ `failed`。

## 五、歧义处理机制

| 场景 | 机制 | 结果 |
| --- | --- | --- |
| 多条同名/相似便签 | `search_notes` 结果末尾附加「以下标题存在多条记录…必须先用 id 确认是哪一条，不要自行挑选或批量修改」 | 模型被明确要求先问；修改/删除仍需要真实 id |
| 一个提醒多个待触发闹钟，未指定 `alarm_id` | `applyReminderTime` 返回 `ambiguous_alarm`，执行器标记 `needsInput` | 不修改任何闹钟，终态「等待用户补充信息」，执行记录显示「等待补充」 |
| 指定 `alarm_id` | 只改目标闹钟的 `remindAt`，保留 `mode / method / interval / intervalMs` | 重复规则（once/loop/daily/weekly/monthly/yearly/lunar/workday）不丢失 |
| 目标、要改的内容、时间不明确 | 提示词规则 13 要求列出候选并询问 | 模型追问；执行层不会「猜一个」 |
| 多个候选提醒 | 提示词要求列出候选并询问 | 不批量修改 |

说明：同名便签的「只能选一条」目前由提示词 + 执行层「必须带 id」共同保证；执行器不提供按标题模糊匹配的写入入口，因此不存在自动选中第一条的代码路径。

## 六、进度反馈

### 6.1 阶段定义

`src/components/AssistantPanel.tsx:262` 的 `PHASE_META`：

| 阶段 | 文案 | 出现时机 |
| --- | --- | --- |
| `understanding` | 正在理解任务 | 首次请求模型前、联网搜索结束后 |
| `searching` | 正在搜索资料 | 联网搜索中；工具批次全部为只读时 |
| `executing` | 正在执行操作 | 工具批次包含写入或删除提议时 |
| `composing` | 正在整理结果 | 工具结果回传后、下一轮请求模型前 |
| `done` | 已完成 | 全部成功且无缺口 |
| `partial` | 部分完成 | 轮次上限 / 部分失败 / 中途停止但有成功项 |
| `failed` | 执行失败 | 请求级错误，或全部步骤失败 |
| `needs_input` | 等待用户补充信息 | 工具返回 `needsInput`（如多闹钟未指定目标） |

### 6.2 展示规则

- 流式过程中：有正文时在正文上方显示带动态点的实时阶段徽标；尚无正文时，思考指示器直接显示当前阶段文案（不再笼统显示「正在思考」）。
- 结束后：非 `done` 的结果显示终态徽标；有执行记录时显示「执行记录 · N 步」。
- 普通纯问答（无工具、无失败）不额外加徽标，保持原有简洁观感，视觉沿用 V0.8 变量与圆角。
- 阶段只在真实节点切换，没有假的百分比或轮播文案；停止后立即收尾，不留长期加载态。

## 七、失败、部分完成与结果小结

### 7.1 执行记录

`AssistantToolStep` 字段：

```ts
{
  callId, tool, label, status, message,
  needsInput?, effect?: { op, kind?, entryId?, title?, count? }
}
```

- `label`：用户可读动作，优先使用工具回读的真实标题（新建 / 修改 / 读取 / 删除 + 「标题」）。
- `effect`：结构化事实来源，面板小结只从这里聚合，不从模型文本推断。
- `status`：`ok / error / cancelled / duplicate / confirm`；`needsInput` 时状态文案为「等待补充」。

### 7.2 小结文案（`executionSummaryLines`）

按真实执行记录生成，可能出现的行：

- `新建 N 项：待办「…」、备忘「…」`
- `修改 N 项：…`
- `等待确认删除 N 项：…`
- `搜索资料 N 次：搜索便签「…」`
- `读取 N 项：…`
- `查看清单 N 次：…`
- `失败 N 项：…`
- `等待补充信息 N 项：…`
- `已跳过重复调用 N 项（未重复写入）`

面板顶部同时显示「执行记录 · N 步」，并在有失败/待补充/删除待确认时用对应颜色标出数量；明细通过「查看每一步」展开，逐步显示状态、标签与工具返回摘要（单步摘要上限 300 字符，完整结果仍回传给模型）。

### 7.3 诚实性保证

- 模型正文之外，轮次上限提示由代码追加，模型无法省略。
- 终态推导采用「宁可少报完成」：`requestFailed → failed`、`needsInput → needs_input`、`limitReached → partial`、部分失败 → `partial/failed`、全部成功才 `done`。
- 停止时不承诺回滚；已提交的写入会在执行记录中保留。
- 兜底路径（异常退出）按「有成功项 → partial，否则 failed」收尾，避免永久「生成中」。
