> 本报告未修改任何产品代码，未创建 Git 提交。
> 对照基线：Phase 3.2 最终版本（当前已暂存，待人工验收）。
> 日期：2026-11-13

## 0. 结论摘要

1. 现有 Agent 已经具备可用的工具调用闭环：参数校验、执行层拦截、删除确认、多闹钟选择、写后回读、批次串行执行都已落地。
2. 但「意图理解」目前几乎全部由提示词承担：没有结构化意图状态、没有确定性的意图分类、没有针对「同名目标」的执行层保护，也没有相对时间的解析回显。
3. Phase 4.1 的最小改造应遵循三层分工：
   - **确定性分类器**：只产出内部意图状态和提示约束，不直接决定是否写入；
   - **提示词**：只做软约束，不承担硬安全；
   - **执行层**：继续承担硬边界，新增「目标 id 必须已在本轮可见数据中出现」与「同名标题写入门禁」。
4. 建议 Phase 4.1 首批只做以下四件事：
   - 意图分类纯函数与内部状态；
   - 本轮可见目标 id 守卫（阻断猜测 id）；
   - 同名目标确定性拦截（阻断默认选第一条）与用户澄清后的放行；
   - 相对时间与多步骤任务的提示约束 + 全链路测试。
5. 同名目标的「点击式候选卡片」是更强的方案，但会引入新的 UI 与一次性授权注册表。本报告给出 A/B 两案，建议 4.1 先用 A 案，B 案是否纳入 4.1 由用户确认。

## 2. 意图识别现状

### 2.1 分层现状

| 层 | 当前做法 | 能力 | 缺口 |
| --- | --- | --- | --- |
| system prompt | `assistantContext.ts:176-180` 五条回答规则 | 说明可查询/新增/修改、删除需确认、信息不足先问 | 纯文本约束，无结构化状态 |
| 工具提示词 | `agentToolSchema.ts:168-173` 第 11-16 条 | 先判断任务类型、多步依赖、歧义先问、结果小结 | 模型可能忽略；无执行层兜底 |
| 工具描述 | `create_entry` / `update_entry` / `delete_entry` | 新增和修改直接生效，删除必须确认 | 模型选错工具时无意图复核 |
| 执行层 | 参数校验 + 闹钟/删除专项拦截 | 硬安全集中在这里 | 没有「意图」概念，也没有同名目标保护 |
| 类型/store | `AssistantMessage` 只有阶段、步骤、动作、候选 | 可展示执行过程 | 没有 intent / confidence / missingInfo |
| UI | 阶段徽标、执行记录、结果小结、删除/闹钟卡片 | 用户能看到「做了什么」 | 看不到「助手理解成了什么」 |

### 2.2 关键事实

- 历史只保留 user / assistant 文本，**不包含历史工具调用与工具结果**；assistant 文本还会剥掉 `<action>` 块（`useAssistantStore.ts:273-289`）。
- `<notes>` 上下文包含条目 id，但只覆盖「当前选中 + 最近 15 条、总计 6000 字」；更早的条目只能靠本轮工具查询拿到 id（`assistantContext.ts:46-50、100-136`）。
- `update_entry` / `delete_entry` 都按 id 定位，**没有按标题匹配**；模型只要给出一个存在但错误的 id，执行层不会发现（`agentToolExecutor.ts:363-371、547-553`）。
- `search_notes` 已经会提示「同名记录」，但只是文本提示，不阻断写入（`agentToolExecutor.ts:212-226`）。
- 相对时间由模型换算成 ISO 字符串；执行层只校验绝对时间是否合法、是否未来（`agentToolArgs.ts:180-197`）。创建结果会回显格式化时间（`agentToolExecutor.ts:314-321`），修改结果也会回显（`:510-512`）。
- 删除提议不会因为「开始新任务」而失效；只有 `clear()` 会重置。新任务只取消候选闹钟授权（`useAssistantStore.ts:207-208、753-759`）。
- `retry()` 会删除最后一条用户消息及其后的消息，然后重新发送同一文本；已提交的写入不会回滚（`useAssistantStore.ts:741-751`）。

## 3. 缺陷清单

> 严重度：P0 = 可能造成错误写入或安全边界缺失；P1 = 明显影响准确性或可恢复性；P2 = 体验/可观测性。

### D1（P0）闲聊/咨询与写入只靠提示词区分

- 证据：`agentToolSchema.ts:168` 第 11 条要求「先判断任务类型」；没有结构化意图状态。
- 影响：「帮我想想怎么整理」「设计一个学习方案」这类请求，模型可能直接调用 `create_entry`；执行层无法判断这是建议还是指令。
- 现状缓解：`create_entry` 参数合法就会写入；同参数去重只在单请求内生效。
- 4.1 处理：确定性分类器 + 提示约束；**不**用分类结果直接禁用工具，避免误判导致漏执行。

### D2（P1）跨轮次目标指代缺少真实 id

- 证据：历史不包含工具结果（`useAssistantStore.ts:273-289`）；assistant 文本中的 `<note-ref>` 也会被解析成纯文本。
- 影响：「把刚才那个待办改到明天」在下一轮可能拿不到 id；模型可能重新搜索、询问，或猜测。
- 4.1 处理：当前选中条目和 `<notes>` 中可见的 id 可支撑一部分场景；完整会话记忆属于 4.2，本阶段不越界。

### D3（P0）同名目标没有执行层保护

- 证据：`search_notes` 只输出「存在多条同名记录」的提示（`agentToolExecutor.ts:212-226`）；`update_entry` 按 id 直接写（`:363-371`）。
- 影响：模型看到两条同名记录后仍可能默认选第一条并成功写入；提示词无法提供确定性保证。
- 4.1 处理：新增「同名标题写入门禁」。A 案：阻断 + 文本候选 + 用户明确澄清后放行；B 案：候选卡片点击授权。见 §5.3。

### D4（P1）相对时间只由模型解析，缺少解析结果确认

- 证据：工具 schema 要求 `YYYY-MM-DDTHH:mm`（`agentToolSchema.ts` create/update 参数）；执行层只校验绝对时间（`agentToolArgs.ts:180-197`）。
- 影响：「下周」「月底」「明早」可能被模型解析错；用户在看到结果前无法确认解析是否符合预期。
- 现状缓解：创建/修改结果会回显绝对时间，但这是事后可见。
- 4.1 处理：提示词要求在回答中先说明解析出的绝对时间；对「月底/下周/过几天」等歧义表达先询问；不新增第二套日期解析器。

### D5（P1）多步骤依赖只靠提示词约束

- 证据：第 12 条要求跨轮次依赖真实 id（`agentToolSchema.ts:169`）；批次语义本身是正确的（`agentExecution.ts:138-200`），但执行层不检查「同一批次的第二个调用是否引用了第一个调用的结果」。
- 影响：模型可能在同一批次里先生成查询、再用猜测的 id 生成修改；查询结果在批次结束后才可见。
- 4.1 处理：分类器标记 `multiStep`，注入「先查询、下一轮再写入」的提示；配合 §5.2 的可见 id 守卫，从执行层阻断猜测 id。

### D6（P1）缺失信息没有结构化原因

- 证据：`ToolOutcome.needsInput` 是布尔值，目前主要由闹钟歧义产生（`agentToolExecutor.ts:495-499`）。
- 影响：目标缺失、时间不明确、修改内容不明确都无法在执行层表达为「需要补充」。
- 4.1 处理：分类器输出 `missingInfo` 枚举（`target` / `time` / `content` / `none`），用于提示约束与开发日志；是否持久化到消息留给 4.3。

### D7（P1）未知意图没有兜底规则

- 证据：提示词没有「无法判断时先询问」的统一规则；工具仍全部可用。
- 影响：模型可能在不确定时直接写。
- 4.1 处理：`unknown` 意图注入「先询问，不要写入」的软提示；硬边界仍由参数校验和可见 id 守卫承担。

### D8（P2）修改字段边界只靠提示词

- 证据：`update_entry` 同时支持 `content`（整体替换）与 `append_content`（追加），schema 描述区分，但没有意图层约束。
- 影响：用户说「补充一下」时，模型可能用 `content` 覆盖原文。
- 4.1 处理：分类器识别「补充/追加」信号，提示明确使用 `append_content`；不新增执行层字段推断。

### D9（P1，跨阶段）重试可能重复创建

- 证据：`retry()` 重新发送最后一条用户消息（`useAssistantStore.ts:741-751`）；写签名只在单请求作用域内（`agentToolExecutor.ts:606-613`）。
- 影响：上次部分成功后重试，可能重复创建相同条目。
- 归属：Phase 4.4 失败恢复与幂等；4.1 只记录，不在本阶段引入跨请求幂等表。

### D10（P2，跨阶段）新任务不会使待确认删除失效

- 证据：新发送只取消候选闹钟（`useAssistantStore.ts:207-208`）；删除提议 TTL 10 分钟（`deleteProposals.ts:32`）。
- 影响：用户开始新任务后，旧删除卡片仍可能被点击执行。
- 归属：Phase 3.2.1 / 4.4 的生命周期复核；4.1 不修改，避免扩大范围。

### D11（P2，跨阶段）缺少意图与耗时可观测性

- 证据：开发日志只记录上下文构建、system 长度、历史条数、首字/总耗时（`useAssistantStore.ts:304` 附近）。
- 影响：无法判断一次错误写入是「分类错」「模型选错」还是「执行层漏拦」。
- 归属：Phase 4.5；4.1 只增加一条开发环境意图日志。

### D12（P2）提示词存在重复与漂移风险

- 证据：`assistantContext.ts:176-180` 与 `agentToolSchema.ts:168-173` 都在描述写入边界。
- 影响：新增动态意图提示时可能与既有规则冲突。
- 4.1 处理：意图提示保持一句话，只补充本轮特有约束，不重复既有规则。

## 4. Phase 4.1 目标与最小改造原则

### 4.1 目标

1. 让「闲聊 / 查询 / 新增 / 修改 / 删除 / 多步骤 / 缺信息 / 未知」在内部有明确表示。
2. 减少三类错误：
   - 把咨询当写入；
   - 把查询当写入；
   - 目标不明确时按标题或第一条猜测写入。
3. 所有新增能力都必须能落到可测试的纯函数或执行层校验，不以「提示词已写」作为验收依据。

### 4.2 原则

- 不新增独立模型调用；意图分类使用确定性规则。
- 不新增依赖、不改数据库结构、不改仓储协议。
- 意图标签**不直接授权写入**，也不单独作为拒绝写入的唯一依据；写入仍必须通过现有参数校验与执行层。
- 硬安全优先放在执行层；提示词只做软约束。
- 不改变 Phase 3.2 的闹钟点击授权与删除确认流程。
- 不进入 Phase 4.2 的会话记忆范围；跨轮指代只使用当前选中条目、`<notes>` 可见条目和本轮工具结果。

## 5. 改造方案

### 5.1 新增意图分类纯函数

建议新增 `src/services/agentIntent.ts`：

```ts
export type AgentIntentKind =
  | 'chat'
  | 'search'
  | 'create'
  | 'update'
  | 'delete'
  | 'unknown'

export type MissingInfoKind = 'none' | 'target' | 'time' | 'content'

export interface AgentIntent {
  kind: AgentIntentKind
  /** 是否包含多个有依赖关系的操作 */
  multiStep: boolean
  missingInfo: MissingInfoKind
  /** high 才注入提示；medium/low 仅记录 */
  confidence: 'high' | 'medium' | 'low'
  /** 命中的规则名，仅用于开发日志与测试 */
  signals: string[]
}

export function classifyAgentIntent(text: string): AgentIntent
export function buildIntentHint(intent: AgentIntent): string | null
```

分类规则见 §7。`buildIntentHint` 只返回一句话，且只对以下情况生效：

- `chat`：本轮更像咨询，先回答；如用户明确要求写入，仍按明确请求执行。
- `search`：本轮是查询，只读不写。
- `unknown`：不确定是否要写入，先询问。
- `missingInfo !== 'none'`：缺少目标/时间/内容，先询问。
- `multiStep`：先查询确认，再在后续轮次写入。
- `delete`：删除必须走确认卡片。

`create` / `update` 且信息完整时不注入提示，避免干扰模型。

### 5.2 本轮可见目标 id 守卫（P0）

目的：从执行层阻断「猜测 id」与「同批次依赖前一个查询结果」。

设计：

1. `buildAssistantContext` 返回值增加 `visibleEntryIds: string[]`，只包含真正写入 `<notes>` 的条目（选中条目 + 实际进入上下文的最近条目）。
2. `AgentToolScope` 增加 `allowedTargetIds: Set<string>`：
   - 创建 scope 时用 `visibleEntryIds` 初始化；
   - `search_notes`、`list_todos`、`list_reminders`、`get_note` 成功执行后，把结果中的 id 加入集合；
   - `update_entry` / `delete_entry` 在写入前检查 `args.id` 是否在集合内。
3. 不在集合内时：
   - `update_entry` 返回 `toolError`，`needsInput: true`，文案：「目标不在本轮可见数据中，请先搜索或读取确认后再修改」；
   - `delete_entry` 同样拒绝，不生成删除卡片。
4. 该守卫只限制「目标 id 来源」，不限制字段修改；已通过搜索/读取拿到的 id 仍可直接写入。
5. 现有单元测试直接调用 `executeToolWithEnv` 时，需要显式把种子 id 放进 scope；未提供时按「测试直连」处理，可通过 scope 构造函数参数区分。

边界说明：

- 这不是权限系统，不替代参数校验；它只保证「模型写入的 id 至少在本轮数据里出现过」。
- 上下文被截断导致旧条目不可见时，模型应先 `search_notes`，这是预期行为。
- Phase 4.2 引入会话记忆后，可以把历史工具结果中的 id 加入允许集合，本阶段不做。

### 5.3 同名目标写入门禁（P0，A/B 两案）

#### A 案：确定性阻断 + 文本候选 + 用户澄清放行（建议 4.1 采用）

1. `search_notes` 命中同名标题时，把规范化标题与候选 id 写入 scope 的 `ambiguousTargets`。
2. `update_entry` / `delete_entry` 写入前，如果目标条目的规范化标题在 `ambiguousTargets` 中：
   - 不写入；
   - 返回 `needsInput: true`；
   - 文案包含候选清单（id、类型、标题、更新时间），要求模型列出候选并询问用户。
3. 放行条件：
   - 当前用户消息包含明确的选择表达（如「第 2 条」「第二个」「标题是 XXX 的那条」「id 是 ...」），分类器输出 `disambiguated: true`，本轮不触发同名阻断；
   - 或目标 id 来自用户在上一轮明确选择后的当前上下文，并且本轮没有新的同名搜索结果。
4. 放行后仍要求执行层按 id 精确写入，不按标题模糊匹配。

优点：不新增 UI、不改持久化结构、能覆盖「默认选第一条」这一主要风险。
缺点：用户澄清仍是自然语言，模型负责把「第二条」映射到 id；不是点击级一次性授权。

#### B 案：同名目标候选卡片（点击授权，复用 Phase 3.2 模式）

1. 新增 `src/services/targetSelections.ts`：候选注册表、TTL、一次性 claim。
2. 新增 `src/services/targetSelectionExecution.ts`：用户点击后按 entryId 执行已授权的更新/删除。
3. `AssistantMessage` 增加 `toolTargetSelections` 等字段；`AssistantPanel` 增加候选卡片。
4. 搜索结果出现同名时生成候选卡片；模型写入被阻断，只有点击才产生授权。
5. 失效规则与闹钟一致：新任务、停止、清理、目标变更、过期、已使用。

优点：点击级一次性授权，安全性最强。
缺点：工作量明显大于 A 案，涉及 UI、store、类型、集成测试；更接近 4.3 的执行体验范围。

建议：4.1 先做 A 案；如果验收要求「同名目标也必须点击授权」，再把 B 案纳入 4.1 或 4.3。

### 5.4 多步骤任务

1. 分类器识别顺序连接词（然后/再/之后/并且/同时）与多个动作动词，输出 `multiStep: true`。
2. 提示：先查询确认目标，下一轮再写入；同一批次的多个调用彼此不可见。
3. 执行层不新增「计划」对象；批次串行语义保持不变。
4. 由 §5.2 的可见 id 守卫兜底：同批次里猜测的 id 会被拒绝。

### 5.5 相对时间

1. 不新增自然语言日期解析器，避免与模型解析产生两套结果。
2. 分类器只识别「不完整/多解释」的时间表达（下周、月底、过几天、晚点、明早等），输出 `missingInfo: 'time'`，提示先确认具体日期。
3. 提示词补充一条：用户使用相对时间时，最终回答必须写出解析后的绝对时间；工具参数必须是 `YYYY-MM-DDTHH:mm`。
4. 执行层继续使用现有 `validateRemindAt`：归整到分钟、必须未来；工具结果继续回显绝对时间。

### 5.6 缺失信息与未知意图

- 目标缺失：分类器识别「这个/那个/它/刚才那个」且当前没有选中条目时，输出 `missingInfo: 'target'`。
- 内容缺失：识别「改一下/优化一下/调整一下」但没有说明改什么时，输出 `missingInfo: 'content'`。
- 未知：没有任何强信号时输出 `unknown`，提示先询问。
- 以上都只是提示；执行层仍按参数校验拒绝非法调用。

### 5.7 可观测性

- 在现有开发日志中增加一行：
  `[AI][intent] kind=... multiStep=... missingInfo=... confidence=... signals=... hint=yes/no`
- 不记录用户原文、不记录密钥、不记录完整 prompt。
- 是否把 `intent` 持久化到 `AssistantMessage` 留给 4.3；4.1 默认不持久化。

## 7. 意图分类规则设计

### 7.1 预处理

1. 去首尾空白，压缩连续空白。
2. 保留中文原文；英文关键词转小写。
3. 不做分词依赖，使用关键词与短语命中，避免引入新依赖。

### 7.2 优先级

```
delete > update > create > search > chat > unknown
```

理由：删除和修改的风险最高，必须先识别；查询与闲聊的误判成本较低。`multiStep` 与 `missingInfo` 独立计算，不参与主优先级。

### 7.3 规则表

| 意图 | 强信号 | 负信号/排除 | 示例 |
| --- | --- | --- | --- |
| delete | 删除、删掉、删了、移除、清除、扔掉、清空 | 「删除功能怎么做」这类咨询 | 「删除这个便签」「把那条提醒删掉」 |
| update | 修改、改、调整、更新、换成、改为、改成、勾选、标记完成、追加、补充、加标签、去掉标签 | 没有目标指代且没有具体字段 | 「把刚才那个待办改到明天」「给这条加标签」 |
| create | 新建、新增、添加、创建、记一下、帮我记、提醒我、建一个、加一个、安排一个 | 「怎么新建」这类咨询 | 「新增一个明天上午的会议提醒」 |
| search | 有哪些、列出、列一下、查一下、找一下、搜索、看看、统计、多少、最近的 | 同时出现明确写入动词 | 「帮我列出今天的待办」 |
| chat | 怎么、如何、为什么、能不能、建议、方案、帮我想想、要不要、值不值得 | 同时出现明确写入动词 + 目标 | 「帮我想想怎么整理这些待办」 |
| unknown | 无强信号，或信号冲突 | — | 「嗯」「那个」「处理一下」 |

### 7.4 置信度

- `high`：只命中一个意图类别的强信号，且没有冲突的写入动词。
- `medium`：命中一个类别，但存在弱冲突信号。
- `low`：多个类别同时命中，或只有模糊指代。

只有 `high` 才注入提示；`medium` / `low` 只记录，不干扰模型。

### 7.5 多步骤识别

满足任一条件即 `multiStep: true`：

- 出现顺序连接词：然后、再、之后、接着、并且、同时、顺便；
- 出现两个及以上不同类别的动作动词；
- 出现依赖表达：把……中的……、根据……、其中的、这些里的。

提示只说明「先查询、下一轮再写入」，不生成计划对象。

### 7.6 缺失信息识别

| 类型 | 信号 | 处理 |
| --- | --- | --- |
| target | 这个/那个/它/刚才那个/上面那条，且当前无选中条目 | 提示先询问或先查询 |
| time | 下周/月底/过几天/晚点/明早/下班前，且没有具体日期 | 提示先确认具体日期 |
| content | 改一下/优化一下/调整一下/处理一下，且没有具体字段 | 提示先询问改什么 |
| none | 未命中 | 不提示 |

### 7.7 与验收用例的对应

| 验收用例 | 分类结果 | 期望行为 |
| --- | --- | --- |
| 普通聊天 | `chat` | 不调用工具 |
| 帮我列出今天的待办 | `search` | 只查询，不写入 |
| 新增明天上午的会议提醒 | `create` + 时间完整 | 直接新增，无确认卡片 |
| 把刚才那个待办改到明天 | `update` + `missingInfo: target`（无选中时） | 先询问或先查询 |
| 删除这个便签 | `delete` | 进入删除确认 |
| 多闹钟目标不明确 | `update` + 闹钟歧义 | 用户点击候选，模型不能自选 |
| 多步骤任务 | `multiStep` | 跨轮次使用真实 id |
| 无效参数 | 任意 | 执行层拒绝，不写入 |

## 8. 操作边界与歧义处理

### 8.1 边界矩阵

| 用户表达 | 意图 | 允许的执行 | 硬边界 |
| --- | --- | --- | --- |
| 「帮我想想怎么安排」 | chat | 只回答 | 无写入工具调用；如模型仍调用，参数/目标守卫仍生效 |
| 「有哪些待办」 | search | 只读工具 | 不写入 |
| 「新增一个提醒」 | create | `create_entry` 直接写入 | 参数校验、长度、时间未来 |
| 「把这条改到明天」 | update | `update_entry` 直接写入 | 目标 id 必须可见；同名需澄清；闹钟需点击 |
| 「删除这条」 | delete | 生成确认卡片 | 用户点击才执行；一次性、TTL |
| 「把这周的待办整理成提醒」 | multi_step | 先查询，后续轮次写入 | 同批次不得依赖未返回的 id；可见 id 守卫 |
| 「处理一下」 | unknown | 先询问 | 不猜测目标与内容 |

### 8.2 同名目标

- A 案：搜索发现同名 → 写入被阻断 → 模型列出候选 → 用户明确选择 → 下一轮放行。
- B 案：搜索发现同名 → 生成候选卡片 → 模型写入被阻断 → 用户点击 → 一次性授权执行。
- 无论 A/B，**模型不得按标题模糊匹配写入**；执行层只接受精确 id。

### 8.3 多闹钟

- 完全沿用 Phase 3.2：模型给的 `alarm_id` 不是授权；多个待触发闹钟必须用户点击候选。
- 4.1 只增加「修改提醒时间前先读取闹钟」的提示，不改变授权实现。

### 8.4 删除

- 完全沿用现有确认机制：`delete_entry` 只生成提议；用户点击才移入废纸篓。
- 4.1 不新增自动删除，也不因为意图分类为 `delete` 就直接执行。

### 8.5 相对时间

- 模型负责把自然语言转成绝对时间；执行层只验证绝对时间。
- 歧义表达先询问；回答中回显绝对时间。
- 不新增第二套日期解析器，避免两套结果不一致。

## 11. 风险与待确认决策

### 11.1 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 确定性分类器误判 | 提示错误，干扰模型 | 只对高置信度注入；提示措辞保留「以用户明确请求为准」 |
| 可见 id 守卫阻断合法写入 | 用户觉得「明明刚说过」却被拒 | 拒绝文案明确要求先搜索；4.2 再补会话记忆 |
| 同名 A 案依赖自然语言澄清 | 模型可能把「第二条」映射错 | 放行后仍按精确 id 写入；必要时升级 B 案 |
| 相对时间歧义 | 解析错误 | 先询问 + 回答回显绝对时间 |
| 提示词膨胀 | 模型注意力下降 | 意图提示只加一句，不重复既有规则 |
| 真实模型不确定性 | 验收波动 | 采用安全结果断言 + 重试记录 |
| 与 4.4 的重试/幂等问题交叉 | 重复创建 | 本阶段只记录，4.4 处理 |

### 11.2 待确认

1. **同名目标采用 A 案还是 B 案？**
   - 建议：4.1 先 A 案；若验收要求点击级授权，再纳入 B 案。
2. **「刚才那个」在 4.1 的边界**
   - 建议：只支持当前选中条目、`<notes>` 可见条目和本轮工具结果；完整跨轮指代留给 4.2。
3. **是否把意图持久化到消息**
   - 建议：4.1 不持久化，只在开发日志记录；4.3 再做用户可见的任务理解摘要。
4. **是否对 `chat` 意图禁用写工具**
   - 建议：不禁用。分类器可能误判，禁用会造成漏执行；用提示 + 执行层守卫。
5. **相对时间是否新增本地解析器**
